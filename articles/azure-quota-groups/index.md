# Research Brief: Azure Container Apps Sandboxes — programmable, stateful isolated compute for untrusted and AI-agent workloads

## Input and scope

- **Exact service/capability:** Azure Container Apps Sandboxes (`Microsoft.App/sandboxGroups`), a first-class Azure Container Apps resource type for running isolated, programmable compute environments.
- **Requested angle:** None supplied; the researcher selected an angle (see below).
- **Candidate URLs:** None supplied.
- **Research date:** 2026-09-30
- **Selected scope:** Azure Container Apps Sandboxes as a distinct, newer capability from Azure Container Apps dynamic sessions — specifically the architectural trade-off of stateful, SDK/CLI-controlled, suspend/resume-capable isolated compute (with built-in egress policy enforcement) versus the older HTTP-routed, ephemeral dynamic-sessions model. This brief covers core behavior, architecture, security/network controls, lifecycle, prerequisites, limitations, and enterprise/regulated-industry implications.
- **Explicit out-of-scope boundaries:** This brief does not cover Azure Kubernetes Service confidential computing, general Container Apps platform features unrelated to sandboxes/sessions (for example, Dapr, ingress, workload profiles generally), non-Microsoft sandboxing products, or performance/benchmark comparisons. It does not treat Azure Container Apps **dynamic sessions** as the primary subject — dynamic sessions are covered only as a contrast point because Microsoft's own documentation positions Sandboxes against them.

## Executive framing

Microsoft documents Azure Container Apps Sandboxes as a new first-class resource type, alongside container apps, jobs, and dynamic sessions, that provides "fast, secure, ephemeral compute environments with built-in suspend and resume capabilities" (C01). The accompanying tooling — a CLI reporting itself as `aca 1.0.0-preview.1` and an ARM API version `2026-02-01-preview` — indicates this is an actively evolving, currently preview-stage capability rather than a mature, long-GA feature (C02, C03). This matters now because enterprises building AI agents and LLM-driven code-execution features need compute that isn't just ephemeral and disposable (as with dynamic sessions) but can hold state, be paused and resumed, and be governed by fine-grained, policy-driven egress control at the moment untrusted code needs to reach external systems (C04, C05, C10).

**Central thesis:** Azure Container Apps Sandboxes shifts the sandboxed-execution trade-off from "disposable and stateless" toward "disposable but stateful and lifecycle-controllable," which is architecturally consequential for regulated enterprises building AI agents — but it does so as a current-preview capability that requires deliberate identity, network, and data-governance validation before production adoption (C01, C02, C11, C15).

## Candidate angles and selection

For this broad-to-narrow input ("Azure Container Apps sandboxes"), the researcher considered two genuine angles:

1. **Sandboxes as the generic dynamic-sessions capability** (isolated code execution for LLM-generated code) — this would conflate "sandboxes" with the older, better-documented "dynamic sessions" feature and would not accurately reflect the term the user specifically invoked.
2. **Azure Container Apps Sandboxes as the distinct, named first-class resource type** (`Microsoft.App/sandboxGroups`) that Microsoft explicitly contrasts with dynamic sessions in its own documentation, emphasizing stateful lifecycle control, suspend/resume, snapshots, volumes, and a dedicated egress-policy engine.

The second angle was selected because Microsoft's own documentation treats "Sandboxes" as a specific, named, and architecturally distinct resource from "dynamic sessions" (C04), and because this distinction — ephemeral/pool-managed versus stateful/developer-controlled — is the more consequential and newly practical architectural decision for platform and security teams. Since the user's input ("Azure Container Apps sandboxes") is itself the exact product name Microsoft uses, manufacturing a second angle beyond this would be artificial; the brief evaluates the supplied topic directly rather than substituting dynamic sessions as the subject, while still using dynamic sessions as a documented comparison point because Microsoft's own material frames the two together (C04).

## Microsoft-stated capability

Microsoft describes Azure Container Apps Sandboxes as providing (C01):

- **Sub-second startup** from prewarmed pools (C06).
- **Strong isolation**: each sandbox runs in its own secure boundary "safe for untrusted code execution" (C06).
- **Scale to zero**: no CPU or memory fees while sandboxes are stopped (C06).
- **Scale-out** to "thousands of concurrent sandboxes on demand" (C06).
- **OCI container image support**: a built-in public image or customer-supplied container images used as sandbox root filesystems (C06).
- **Suspend and resume**: full-state snapshots (memory and disk) with "sub-second restore times" (C06).
- **Lifecycle control**: snapshots, persistent storage, and ingress/egress networking policy management (C06).

Architecturally, Microsoft documents a two-plane design: an ARM control plane (`management.azure.com`) for creating, updating, deleting, and listing sandbox groups and managing VNet connections, and a data plane (`management.azuredevcompute.io`) for all per-sandbox operations — running commands, managing files, snapshots, volumes, secrets, ports, and egress policies (C07). A **sandbox group** (`Microsoft.App/sandboxGroups`) is the ARM-level management boundary that scopes sandboxes, disk images, snapshots, volumes, and secrets (C08). Individual **sandboxes** are isolated compute instances with their own CPU, memory, disk, and network boundary, created from a disk image or snapshot, assigned one of five documented resource tiers — XS (0.25 core/0.5 GB/20 GB disk) through XL (4 cores/8 GB/80 GB disk), with M (1 core/2 GB/20 GB) as default (C09).

Microsoft documents two volume types that can be mounted for persistent storage: **Azure Blob** volumes (mountable to multiple sandboxes at once, for shared data) and **Data Disk** volumes (mountable to only one sandbox at a time, for databases and build caches) (C10). Microsoft documents interaction surfaces including a portal (Sandboxes portal), an `aca` CLI, a Bicep/ARM template resource, and a Python SDK (`azure-containerapps-sandbox`) alongside a REST API (C11, C12). Microsoft separately documents an installable "agent skill" — distributed via GitHub Copilot CLI or Claude Code plugin mechanisms — that teaches a coding agent to create and manage sandbox groups and sandboxes, execute commands, set egress policies, snapshot/stop/resume state, and mount volumes, by invoking `aca` CLI commands on the agent's behalf (C36).

A distinct, documented **egress policy engine** ships with every sandbox and governs outbound traffic: policies specify a default action (`Allow`/`Deny`), rules matching on host/path/HTTP method with `Allow`, `Deny`, `Transform`, and `Rewrite` actions, and a traffic-inspection mode (`Full`, `Partial`, `None`, or `Legacy`) (C13, C14). Microsoft documents that `Transform` actions can inject headers from a static value, a secret reference (from the sandbox group's secrets store), or a managed-identity-issued token, explicitly for scenarios where "the agent needs to call an LLM API, but without the agent code to handle the API key directly" (C15).

Microsoft explicitly and directly contrasts Sandboxes with dynamic sessions in its own comparison table (C04): dynamic sessions are accessed via HTTP request routing through a pool management endpoint, are ephemeral and destroyed after cooldown, offer no persistent storage, and provide basic isolation; Sandboxes are accessed via direct SDK/CLI control of individual sandboxes, are stateful with suspend/resume/snapshot support, offer persistent volumes, and provide egress policies, VNet integration, and port management. Microsoft's stated guidance: "Choose dynamic sessions when you need a managed execution experience that abstracts infrastructure. Choose Sandboxes when you need programmable control over isolated compute with state persistence" (C04).

## Benefits and differentiated value

The sourced, differentiated trade-off is **stateful, developer-programmable lifecycle control versus abstracted, pool-managed ephemerality**. Where dynamic sessions optimize for "don't think about infrastructure, just call an endpoint," Sandboxes trade some of that abstraction for direct control: explicit create/suspend/resume/delete operations, snapshotting of full memory+disk state, attachable persistent volumes, and a programmable egress-policy engine applied at the individual sandbox or sandbox-group level (C04, C06, C10, C13).

Microsoft documents this as enabling scenario patterns such as "AI code execution with state preservation" (suspend between agent tasks and resume with full context intact) and "agent workflows" (persistent, isolated workspaces across task boundaries) — presented by Microsoft as suitability guidance in a "when to use sandboxes" table, not as customer-proven outcomes (C05). No performance benchmarks, adoption figures, or comparative claims against non-Microsoft sandboxing products are documented and none should be inferred.

The egress-policy `Transform`/`Rewrite` mechanism is a differentiated security control: it lets an operator front outbound calls from untrusted sandboxed code with policy that injects credentials from a managed identity or secret store, so "the sandbox [is] never needing to hold the credentials directly" (C15). This is a documented architectural technique for limiting credential exposure to untrusted code, not a guarantee that any given workload is secure.

## Maturity, availability, and dates

Evidence of current maturity is indirect but consistent and comes from multiple fetched pages rather than a single explicit "public preview" label on the Sandboxes overview page itself:

- The documented `aca` CLI, when installed per Microsoft's quickstart instructions, reports its version as **`aca 1.0.0-preview.1`** (C02).
- The documented Bicep/ARM resource type is versioned **`Microsoft.App/sandboxGroups@2026-02-01-preview`**, including its `vnetConnections` child resource (C03).
- No fetched Sandboxes page (overview, egress-policies, agent-skills quickstart, or any language/tooling quickstart) contains an explicit "generally available" or GA statement for the Sandboxes feature as a whole.

Given the `-preview` suffix present in both the CLI version and the current ARM API version across every fetched Sandboxes quickstart, this brief treats **Azure Container Apps Sandboxes as a current-preview capability** as of the retrieval date. No Microsoft source establishes a GA date, and no fetched source contradicts the preview signal. This is a preservation of the most specific status evidence found, per the requirement to never infer GA from silence; equally, no page used the literal words "public preview" for Sandboxes, so this brief flags the status as **version-evidence-based preview, not an explicit label**, and calls out this precise gap rather than asserting a definitive maturity word.

By contrast, Microsoft's separate "What's new in Azure Container Apps" page explicitly labeled **dynamic sessions** "Public preview" in its May 2024 entry (C16), and that page states post-November-2024 updates are tracked only in a GitHub location outside this brief's allowed source list, so current dynamic-sessions GA/preview status cannot be confirmed from allowed sources either (C17). This is a documented gap, not an inferred status.

Region scope: the fetched dynamic-sessions overview documents a specific supported-region list for that feature (C18), but no fetched Sandboxes-specific page presented an equivalent supported-region table; Sandboxes quickstarts use `westus2`/`westus3` only as example regions in command syntax, not as a documented availability boundary (C19). Regional availability for Sandboxes should be treated as an open validation question.

## Prerequisites, limits, and caveats

Documented prerequisites and constraints for Sandboxes:

- **Role-based access control is mandatory**: creating or managing sandboxes requires the Azure role **"Container Apps SandboxGroup Data Owner,"** assigned at subscription or resource-group scope; without it, "you can't perform sandbox operations" (C20).
- **Microsoft Entra ID is required**: "Only Microsoft Entra ID accounts can access sandboxes. Personal Microsoft accounts aren't supported" (C21).
- **VNet connection is immutable after creation**: "You can't change the VNet connection's subnet after creation. Size the subnet for peak sandbox concurrency before you deploy" (C22).
- **VNet delegation requirement**: a connected subnet "must be delegated to `Microsoft.App/environments`"; notably, Microsoft states "No managed environment is required" to establish this VNet connection for a sandbox group (C23).
- **Resource tiers are fixed**, not arbitrary custom sizing: five named tiers (XS through XL) define CPU/memory/disk combinations, though a sandbox group's Bicep definition can also set group-level defaults (`defaultCpu`, `defaultMemory`, `defaultDisk`) (C09).
- **Volume mount constraints differ by type**: Data Disk volumes are single-sandbox-only; Blob volumes can be shared across multiple sandboxes (C10).
- **Egress policy evaluation caveat**: "Policies are mutable on running sandboxes. Updates apply to subsequent requests; in-flight requests aren't reevaluated" (C24).
- **Traffic-inspection trade-off**: setting inspection to `None` "trades safety for latency" and should be reserved for sandboxes that don't run untrusted code and only for trusted destinations (C25).

No fetched source documents an SLA specifically for Sandboxes (the general Container Apps pricing page links only to a general Container Apps SLA page, not a Sandboxes-specific one), disaster-recovery/backup guarantees for snapshots, data-residency or sovereignty commitments, or quota ceilings for sandbox groups or concurrent sandboxes per subscription beyond the customer-configurable `maxSandboxCount` property. These are documented gaps, not confirmed limits, and must be validated directly with current Microsoft account teams or documentation before production commitments are made.

## Enterprise architecture and operating implications

**Identity and access boundaries:** Microsoft documents role-based gating via the "Container Apps SandboxGroup Data Owner" role as the sole path to create/manage sandboxes, and supports both system-assigned and user-assigned managed identities on a sandbox group, used for gateway connections and registry access (C20, C26 — factual, Microsoft-stated). *Architect interpretation:* because this single role appears to govern the full data plane (execute commands, manage files, snapshots, secrets), organizations should treat it as a highly privileged role requiring the same scoping discipline as `Owner`/`Contributor` assignments, and should evaluate least-privilege boundaries per sandbox group rather than subscription-wide grants (interpretation grounded in C20).

**Network isolation and connectivity:** Microsoft documents VNet connection support via a delegated subnet, with an explicit statement that no managed Container Apps environment is required to attach a VNet to a sandbox group (C23), plus a purpose-built egress-policy engine with default-deny guidance for untrusted-code workloads (C13, C14, C24). *Architect interpretation:* the "no managed environment required" design implies Sandboxes can be provisioned and network-isolated as a standalone resource outside existing Container Apps environments, which changes how network and platform teams should inventory and govern this resource type distinctly from container apps and dynamic sessions (interpretation grounded in C07, C23).

**Encryption, key management, data handling, residency, sovereignty:** No fetched source makes an explicit claim about encryption at rest for snapshots/volumes, key management options (for example, customer-managed keys), or data residency/sovereignty commitments for Sandboxes. This is an unresolved adoption question, not a documented capability.

**Logging, monitoring, auditability, policy, governance:** Microsoft documents an "audit cadence" recommendation to "pull egress decisions periodically from long-running sandboxes and review denied counts," noting "a spike usually indicates a workload misconfiguration or an exfiltration attempt" (C27). No fetched Sandboxes-specific page documents Azure Monitor/Log Analytics table names or metrics equivalent to those Microsoft documents for dynamic sessions (C28, C29); this is a documented gap for Sandboxes specifically, separate from the confirmed dynamic-sessions logging model.

**Compliance documentation and shared-responsibility boundaries:** No fetched source states that Sandboxes carries any compliance certification, and none should be inferred. Using Sandboxes does not, per this brief's evidence and the requirements' fidelity rules, make any workload or organization compliant; that determination requires customer-side validation against workload-specific regulatory requirements.

**Availability, resilience, backup, recovery, service limits:** Snapshots provide a documented mechanism for preserving sandbox state across suspend/resume cycles (C06), but no fetched source describes formal backup/recovery SLAs, replication, or documented service limits (maximum sandboxes per group, maximum groups per subscription) beyond the `maxSandboxCount` property being customer-configurable per group (C30). This remains an adoption question.

**Cost drivers, capacity, quotas, operational ownership:** Microsoft states that "Azure Container Apps Express and Sandboxes follow the same pay-per-second pricing as Consumption Plan" (C31) and that scale-to-zero means "you pay no CPU or memory fees when sandboxes are stopped" (C06). Detailed per-meter Sandboxes pricing (distinct from dynamic sessions' documented session-hour and Dedicated-plan billing models, C32) was not found in the fetched Azure pricing or billing pages beyond the general Consumption-plan-alignment statement; exact rate tables should be validated directly.

**Lifecycle, support, deployment prerequisites, change management:** Documented lifecycle states are limited to "Running" and "Stopped," with configurable auto-suspend (idle timeout), suspend-mode (memory vs. disk-only snapshot), and auto-delete policies (C33). *Architect interpretation:* because the feature carries preview-tagged CLI and API versions (C02, C03), operations teams should expect schema and behavior change between preview iterations and should not encode hard dependencies on the current `2026-02-01-preview` API surface without a validated upgrade plan (interpretation grounded in C02, C03).

## Regulated-industry implications

Supported control considerations documented by Microsoft that regulated-industry teams can rely on as factual starting points:
- Mandatory Entra ID authentication (no personal Microsoft accounts) (C21).
- A dedicated, mandatory RBAC role gating all sandbox create/manage operations (C20).
- A default-deny-capable egress policy engine explicitly recommended for untrusted-code workloads (C14).
- Credential-injection patterns (`Transform` with secret or managed-identity references) designed to keep API keys out of sandboxed/untrusted code paths (C15).

**Customer responsibilities and unsupported decision areas:** Microsoft does not document, in any fetched source, a Sandboxes-specific compliance certification, data residency guarantee, encryption-at-rest specification, formal SLA, or backup/recovery commitment. Regulated-industry teams must not treat use of Sandboxes as satisfying a specific regulatory control; each of the following is an open, workload-specific validation question rather than an answered one:
- What data residency and cross-region replication behavior applies to snapshots and volumes in the customer's target regions?
- What encryption mechanisms (at rest, in transit) and key-management options apply, and are customer-managed keys supported?
- What formal SLA, if any, currently covers Sandboxes distinct from the general Container Apps SLA?
- What audit-log retention, export, and SIEM-integration options exist for sandbox lifecycle and egress-decision events, beyond the documented "pull egress decisions periodically" guidance (C27)?
- Given the preview-tagged API/CLI versions, what is Microsoft's current guidance on production use, breaking-change notice periods, and support commitments during preview (C02, C03)?
- Given that agent skills can be installed to let a coding agent issue `aca` CLI commands autonomously, what approval and change-control gates should govern an agent's ability to create, modify, or delete sandbox infrastructure on an engineer's behalf (C36)?

## Possible use cases

**Hypothetical use case 1 — AI coding agent with persistent, suspendable workspace.** A regulated enterprise's internal developer-tooling team could evaluate using a sandbox group to give an AI coding agent an isolated Ubuntu-based workspace that installs dependencies and builds context over a multi-step task, is suspended between agent turns to avoid paying for idle compute, and is resumed with full memory/disk state intact for the next step. This is technically consistent with Microsoft's documented suspend/resume/snapshot behavior and stated fit for "AI code execution with state preservation" and "agent workflows" (C05, C06). Applicability conditions: requires validating snapshot restore reliability, cost at scale for the specific idle/active pattern, and confirming acceptable production-readiness given the preview-tagged API (C02, C03). This is a scenario to validate, not a deployed or promised outcome.

**Hypothetical use case 2 — Multitenant, egress-locked execution for user-submitted code in a SaaS product.** A platform team building a SaaS feature that executes end-user-submitted or LLM-generated code could evaluate a sandbox group per tenant or per session, using a default-deny egress policy with an explicit allow list for only the destinations that workload needs (for example, an internal API gateway), and `Transform` header injection so the sandboxed code never holds a raw API key. This is consistent with Microsoft's documented "hostile, multitenant scenarios" framing for isolated execution, the egress policy model's default-deny recommendation, and the credential-injection pattern (C05, C13, C14, C15). Applicability conditions: requires validating tenant-isolation boundaries at scale, confirming RBAC scoping for the "SandboxGroup Data Owner" role across tenant boundaries, and validating logging/audit sufficiency for the organization's compliance obligations (C20, C27) — none of which is guaranteed by the documented capability alone.

## Adoption questions and practical next steps

Workload-fit and validation questions for a bounded pilot:

1. **Preview posture:** Given the CLI (`1.0.0-preview.1`) and ARM API (`2026-02-01-preview`) version evidence, what is Microsoft's current support commitment, and is production use currently recommended by Microsoft for this specific workload class? Validate directly before any production commitment (C02, C03).
2. **Identity and RBAC scoping:** How will the organization scope the "Container Apps SandboxGroup Data Owner" role to avoid over-broad privilege, especially across multitenant or multi-team sandbox groups (C20)?
3. **Network boundary design:** Will the sandbox group's VNet connection meet the organization's network segmentation and peak-concurrency sizing needs, given the connection is immutable once created (C22, C23)?
4. **Egress governance:** Can the organization define and maintain default-deny egress policies with the necessary allow-list granularity for its untrusted-code scenarios, and does its audit tooling consume the documented egress-decision data adequately (C14, C24, C27)?
5. **Data handling and residency:** What encryption, residency, and backup guarantees apply to snapshots and volumes in the organization's required regions — none of which is documented in the fetched sources and all of which require direct validation?
6. **Cost model fit:** Does the "pay-per-second, Consumption-plan-aligned" pricing model documented for Sandboxes align with the workload's expected suspend/resume cadence and scale pattern, and are there Sandboxes-specific meters beyond the general statement found (C06, C31)?
7. **Agent-driven infrastructure changes:** If adopting the documented agent skill, what human-approval gates and change-control policy will govern an autonomous agent's ability to create, mutate, or delete sandbox infrastructure via natural-language instructions (C36)?
8. **Comparison against dynamic sessions:** For workloads that don't need persistent state or fine-grained lifecycle control, does the simpler, pool-managed dynamic-sessions model (with its own separately documented preview status, C16) better fit the abstraction level the team wants (C04)?

A bounded pilot path consistent with the evidence: provision a single sandbox group in a non-production subscription, apply a default-deny egress policy with a narrow allow list, exercise the full create → run → suspend → resume → delete lifecycle with a representative disk image, and validate RBAC, logging export, and cost behavior before scoping any production rollout — while tracking Microsoft's documentation for an explicit GA statement.
